# 相似平台启动与功能契约

> 本文回答一个具体问题：基于本仓库的 ARC 文档，能否快速启动一个相似平台，以及启动后哪些能力必须继续存在。
>
> 结论：可以把本仓库作为可运行的参考实现，但 ARC 文档本身不是脱离代码即可复制的模板。新平台必须先完成本文的“最小启动路径”和“功能基线”，再替换领域数据源、品牌文案和业务工具。

## 1. 参考实现的边界

### 可直接复用的基础设施

- React 19 + Vite 7 + TypeScript 的单页应用骨架；
- `functions/<domain>-chat` 的 OpenAI 兼容 tool-calling 编排方式；
- `server/local.mjs` 的 Node 自托管壳、SSE 下行、CORS、断连取消和统计落盘；
- `server/account-api.mjs` 的本地账号、历史快照、访客/登录榜单接口；
- Supabase 可选云模式与未配置时的离线游客模式；
- Docker Compose 的 nginx 静态站点 + chat 服务双容器部署；
- i18n、亮暗主题、响应式布局、桌宠事件总线和本地偏好存储的分层方式。

### 不能直接复制的领域实现

- `seqout-chat` 中的 26 个组学工具、GSE→PRJ/SRP 解析和 seqout API 字段；
- GEO/SRA/ENA/GSA 的编号链接、文献证据链和数据集卡片字段；
- “寻宝鼠/阿寻”品牌、桌宠资源、成就阈值和矿洞主题文案；
- `profiles`、`chat_sessions`、`user_stats` 等 Supabase 表结构及其 RLS；
- `system prompt` 中的领域术语、工具选择规则和空结果口径。

替换领域数据源时，保留服务边界和协议形状，重新定义工具 schema、卡片 schema、错误分类、权限策略和验收夹具。不要把领域名称替换后继续沿用未经核实的编号解析或数据字段。

## 2. 最小可运行路径

### 前置条件

| 项目 | 要求 |
|---|---|
| Node | `>=22.6`（本地服务直接运行 TypeScript） |
| pnpm | 与锁文件兼容的 pnpm 版本 |
| Docker | 仅 Docker 部署需要 |
| LLM | 一个 OpenAI 兼容的 `/models` 与 `/chat/completions` 服务 |
| 数据 API | 至少一个可由服务端访问的只读数据源 |

### 本地启动

```bash
pnpm install
cp server/.env.example server/.env
# 编辑 server/.env，填写 LLM_API_KEY、LLM_BASE_URL、LLM_MODEL
pnpm run server   # http://localhost:8787
pnpm run dev      # http://localhost:3015
```

浏览器先访问 `http://localhost:3015`。发送一条最小问题，并确认同时满足：

1. 页面建立 SSE 连接并持续收到 `delta`；
2. 工具调用能显示 `tool` 事件；
3. 结果卡片（若该问题产生结果）通过 `cards` 事件渲染；
4. 结束帧为 `end`，客户端随后收到 `[DONE]` 或等价终止信号；
5. 刷新页面后游客会话仍在 localStorage 中。

### Docker 启动

```bash
cp server/.env.example server/.env
# 编辑 server/.env，填写真实 LLM_API_KEY
make docker-start
```

默认访问 `http://localhost:10087`（默认端口 10087，`server/.env` 的 `WEB_PORT` 按服务器实际可用端口覆盖；被其他进程占用时 `make docker-start` 会报错停止，重启已有容器不受影响）。改动 `VITE_*` 构建期变量必须重新执行 `make docker-start`；只改运行时密钥或端口可执行 `make docker-restart`。

## 3. 开工前准备清单

开发相似平台前，先把下面的输入物准备齐。没有这些内容，可以搭壳，但无法验证平台是否真的可用。

### 3.1 产品与领域定义（必须）

- 一句话定位：用户是谁、要完成什么任务、结果是什么；
- 领域词汇表：对象名称、编号格式、同义词、中文/英文写法；
- 3 至 5 条真实用户问题，覆盖正常、空结果和错误场景；
- 结果展示草图：列表/卡片/表格字段、来源链接、下载或下一步动作；
- 权限与数据边界：哪些数据公开、哪些需要登录、哪些不能交给模型。

### 3.2 图片与前端素材（必须有占位，正式上线前替换）

| 素材 | 最低准备 | 约束 |
|---|---|---|
| 品牌标识 | SVG 或透明 PNG、深浅背景各一份 | 记录授权来源；不要依赖带鉴权参数的 CDN |
| 首屏/空态图 | 1 张桌面端、1 张移动端可裁切图 | 真实表达产品对象，不用纯装饰背景替代内容 |
| 图标 | 功能图标清单，优先使用现有 icon 库 | 统一尺寸、描边和 hover 语义 |
| 状态图 | 加载、成功、空结果、错误、离线 | 每个状态至少有文字 fallback，不能只靠图片 |
| 桌宠/角色（如保留） | idle、工作、成功、失败、睡眠等状态图 | 透明背景；建议 512px webp，保留原始母版和授权记录 |
| 分享与 favicon | OG 图、favicon、应用图标 | 构建后检查路径和暗色背景可读性 |

素材目录、命名、尺寸和压缩方式要写进样式规范；新增状态图时同时更新状态机表、动效清单和 reduced-motion 规则。

### 3.3 外部 API 与凭据（必须）

- LLM 网关：确认 `/models`、`/chat/completions`、流式格式、工具调用格式和模型上下文上限；
- 领域数据 API：基础 URL、鉴权方式、速率限制、分页、超时、空结果和 4xx/5xx 语义；
- 证据/链接 API（如文献、地图或文件服务）：来源 URL、缓存规则和引用展示要求；
- 账号与存储：Supabase 表/RLS，或自托管账号、历史和统计的落盘目录；
- 部署凭据：域名、TLS、LLM key、数据 API key、可选 NCBI/API email 等；
- 每个密钥的保存位置和轮换方式。密钥只能在 `server/.env`、部署 secret 或平台 secret 中，不能进入前端 bundle、提示词或 Git。

先用 curl 或一个最小 Node 脚本验证每个 API，再接入 tool-calling。把成功响应、空响应和错误响应脱敏后保存为离线 fixture。

### 3.4 提示词与模型行为（必须）

至少准备四份可评审文本，而不是只写一段 system prompt：

1. **系统提示词**：角色、任务边界、工具选择顺序、引用要求、禁止编造、语言和格式；
2. **工具说明**：每个参数的类型、取值约束、何时调用、空结果含义和不要调用的情况；
3. **结果呈现规则**：卡片字段、编号链接、来源引用、下载链接和 `:::followup` 等协议围栏；
4. **错误与安全规则**：超时、限流、敏感请求、权限不足、数据缺失时模型应如何回答。

为每条规则配至少一个黄金问题和期望行为。提示词改动要跑离线对话夹具，不能只凭一次人工试问判断“效果没问题”。

### 3.5 MCP / 工具接口（按需，但领域平台通常必须）

如果数据能力来自 MCP，开工前准备：

- MCP server 的 transport（stdio/SSE/HTTP）、启动命令、版本和健康检查；
- 工具清单：名称、JSON Schema、必填参数、返回结构、错误码、幂等性和速率限制；
- 工具到产品能力的映射：哪些工具暴露给模型，哪些只在服务端组合调用；
- 结果瘦身策略：送给 LLM 的摘要上限、给前端的完整卡片字段、敏感字段脱敏规则；
- 连接失败、工具超时、空结果和部分成功的统一错误模型；
- 若不运行 MCP 进程而改成原生 HTTP/function calling，记录等价契约和差异，避免前端依赖 transport 细节。

本仓库采用“服务端声明式 function schema + 直接调用只读数据 API”的方式。迁移到真正的 MCP 时，仍要保持服务端掌握密钥、前端只接收受控事件，并为工具结果建立 fixture 和回归测试。

### 3.6 验证材料（必须）

- 一份脱敏的 `.env.example`，列出变量用途、默认值、是否构建期；
- 一组 API fixtures：正常、空结果、限流、鉴权失败、超时；
- 一份端到端验收表：启动、登录、发送、流式、卡片、刷新、移动端、暗色、容器重建；
- 一份数据与素材授权记录；
- 一份变更影响表：改工具、协议帧、i18n、主题、数据库时要更新哪些文档和测试。

## 4. 必须保留的功能基线

下表是“相似平台”仍属于本项目体系的最低功能，而不是可选模板装饰：

| 基线 | 当前实现 | 新平台验收证据 |
|---|---|---|
| 对话编排 | tool-calling 循环、流式文本、工具进度 | 一次请求能看到 `delta/tool/end`，异常可读且不会挂死 |
| 结果表达 | 独立 `cards` 事件、Markdown、编号链接 | 卡片不因 LLM 文本截断而丢失，链接可打开来源 |
| 空结果与错误 | 空数据和真实错误分开统计 | 空结果不被当成服务故障，错误包含可定位原因 |
| 会话 | 游客 localStorage；登录后历史快照同步 | 刷新、登录合并、登出后边界行为可复现 |
| 身份 | Supabase 云模式或自托管账号模式 | 未配置云服务时仍可游客使用，账号数据隔离 |
| 统计 | chats / digs / treasures 及周维度 | 重复事件不重复计数，跨周归零有测试或人工证据 |
| 国际化 | zh/en 键同步，组件不写死文案 | `tsc` 通过且两份字典键集合一致 |
| 主题与无障碍 | 亮/暗 token、reduced-motion | 主题切换不闪白，动效关闭后仍可完成主流程 |
| 移动端 | 触摸、软键盘、安全区 | 375px 宽度可输入、发送、查看结果和关闭抽屉 |
| 持久化 | Docker `/app/data` 命名卷 | 重建容器后账号、历史、统计仍存在 |

桌宠、排行榜和成就可以按产品定位替换，但如果保留这些入口，必须同时保留其状态持久化、事件去重、设置同步和 i18n 契约，不能只复制视觉组件。

## 5. 新领域的替换顺序

1. **先定数据契约**：列出工具输入/输出、来源 URL、空结果、超时和权限错误；
2. **再改服务端**：替换 `TOOL_DEFS`、`executeTool`、领域错误分类和卡片抽取；
3. **同步协议**：若新增事件，服务端、`src/services/seqoutChat.ts`、路由编排三处一起改；
4. **同步前端**：卡片、编号链接、输入示例、空态和关于页全部走 i18n；
5. **最后换品牌与视觉**：资产、token、主题文案和桌宠行为都要更新对应 ARC 文档；
6. **建立夹具**：为每个关键映射和错误分支加入离线 fixture，避免真实 API 变化掩盖回归。

## 6. 提交前验收

```bash
npx tsc --noEmit
npx vite build
npm test
```

涉及真实数据源解析、工具 schema、协议帧或错误分类时，再执行：

```bash
npm run test:live
```

视觉变更需检查亮色、`?theme=dark`、375px 和桌面宽度；部署变更需执行 `make docker-start`，并确认 `/app/data` 卷与 SSE 反代配置。文档变更需同步根 `README.md`、`docs/README.zh-CN.md` 和 `src/routes/about.tsx` 中受影响的功能描述。

## 8. 本次审计发现的待清理项

- `package.json` 仍声明 `framer-motion`，但当前源码没有使用；现行规范要求 CSS keyframes，后续依赖清理时应移除该遗留依赖，避免把它当成允许的实现方式；
- 本地开发服务默认端口统一为 `8787`。若项目改端口，必须同时更新 `CHAT_API_PORT`、`VITE_CHAT_API`、Vite proxy target、README 和本文件；
- `qmuse/qmuse-app/` 是停止维护的迁移归档，不纳入新平台的回归和功能同步范围。
